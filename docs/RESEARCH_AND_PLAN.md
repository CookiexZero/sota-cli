# Sota CLI для Docker: исследование и план

Implementation update: see [IMPLEMENTATION.md](IMPLEMENTATION.md) for the working CLI, both architectures, and real-network verification.

Дата: 2026-11-08. Анализ конкретного предоставленного пакета; поведение других версий может отличаться.

## Вывод

CLI технически реалистичен. Первая версия должна управлять штатным `kittend`, извлечённым из `.deb`. Графический интерфейс уже отделён от VPN-ядра Unix-сокетом. Самая существенная неизвестная — воспроизведение получения конфигурации через API Sota по ключу доступа.

Предлагаемый стек: Go для CLI и управляющего процесса, штатный `kittend` для VPN, Docker Compose для подключения других контейнеров. Сначала доказать подключение с импортированной конфигурацией, затем реализовать полноценный вход по ключу.

## Локальный протокол

Из Go runtime metadata восстановлены JSON-поля запросов и ответов. Дизассемблирование записи показывает JSON с завершающим байтом `0x0a`, а обработчик клиента использует сканирование входящих сообщений. Это собственный RPC с JSON-строками; наличие полей `id/method/params` само по себе не означает полную совместимость с JSON-RPC 2.0.

Обработчик `dispatch` содержит команды `hello`, `start`, `stop`, `status`, `forget`, `checkConfig`, `setFileLogging`. В `hello` проверяется `protocolVersion == 1`. Формат первой команды, восстановленный статически:

```json
{"id":1,"method":"hello","params":{"protocolVersion":1}}
```

После каждой команды нужен перевод строки. `hello` также допускает `token`; необходимость токена в выбранном способе запуска проверить при первом запуске. В Debian доступ к сокету ограничивается группой, но нельзя переносить это как единственный механизм доступа на другие режимы запуска.

В `start.params` есть два строковых поля:

- `configuration`: строка конфигурации; допустимое содержимое и преобразование серверного ответа нужно подтвердить.
- `localOptionsJson`: строка с JSON локальных параметров.

Среди локальных параметров восстановлены `network_stack`, `mtu`, `ipv6`, `dns_servers`, `dns_strategy`, `bypass_lan`, `strict_route`, `split_tunnel`, `interface_name`, `inbound_mode`, `proxy_port`, `kill_switch`. Ответ `status` содержит `state`, `connected_since`, `error`, опциональные `kill_switch` и `proxy_port`.

CLI должен различать ответы по ID и асинхронные события состояния, статистики, логов и ошибок. Нужны дедлайны, ограничение размера сообщения и явная ошибка несовместимой версии протокола.

Свидетельства: [JSON-поля](evidence/recovered-json-fields.json), [запись перевода строки](evidence/rpc-newline-framing.asm.txt), [обработчик команд](evidence/dispatch.annotated.asm.txt).

## Два режима для Docker

### TUN для других контейнеров — рекомендуемая основная цель

`sota-cli run --mode tun` запускает демон, получает конфигурацию, поднимает VPN и остаётся работающим управляющим процессом. При SIGTERM корректно завершает дочерний процесс и работу туннеля.

Начальные требования для проверки: Linux Docker Engine, доступ к `/dev/net/tun`, capability `NET_ADMIN`; необходимость `NET_RAW` и остальных прав определить экспериментально. `privileged`, host networking, host PID namespace и права чтения чужих процессов не включать по умолчанию. Per-app split tunneling не входит в MVP.

Другие приложения подключаются через `network_mode: "service:vpn"`. Сам факт общей Docker bridge-сети трафик через VPN не направляет. Публиковать входящие порты приложений в этом случае нужно на VPN-сервисе. Общий network namespace не делает `/etc/resolv.conf` общим: DNS приложений настраивается и проверяется отдельно.

На macOS такой VPN работает внутри Linux VM Docker и не становится автоматически VPN для всей macOS.

### Локальный HTTP/SOCKS-прокси — удобен для первого доказательства

В ядре есть `inbound_mode: "proxy"`, `proxy_port` и сборщик inbound типа `mixed`. Дизассемблирование показывает фиксированный адрес `127.0.0.1` и тег `proxy-in`.

Из этого следует: режим, вероятно, позволяет начать без TUN и сетевых capabilities, но это ещё не проверено запуском. Клиенты в общем network namespace смогут обращаться к loopback-порту. Обычный Docker `ports` сам по себе не откроет listener, привязанный только к loopback контейнера. Для доступа с хоста понадобится отдельный ограниченный relay/listener либо иной подтверждённый способ настройки адреса. Такой relay не включать в первый технический прототип.

Прокси обслуживает приложения, явно использующие его; он не заменяет маршрутизацию всего контейнера через TUN.

Свидетельство: [сборщик proxy inbound](evidence/buildProxyInbound.annotated.asm.txt), ссылки на строки `mixed`, `proxy-in`, `127.0.0.1` в ELF по адресам `0x1aa2560`, `0x1aa2570`, `0x1aa2580`.

## API Sota: главная неопределённость

В Flutter AOT обнаружены следующие пути:

```text
/api/v1/public/subscription/profile
/api/v1/public/connection/list
/api/v1/public/connection/connect
/api/v1/public/connection/disconnect
```

Также присутствуют имена заголовков `X-Access-Key`, `X-HWID`, `X-Device-Name`, `X-App-Version`, `X-Timestamp`, `X-Signature`, а также `X-API-KEY`. Наличие строк не доказывает, что все заголовки обязательны или используются одновременно.

Есть классы/модули `request_signer`, `signing_interceptor`, `secret_obfuscation`, `actualized_autograph`, `spki_pinning`, `actualization_service`, `domain_health_manager`, `blocked_dns_fallback`, `sota_start_request_source`, `singbox_config_adapter`.

Это свидетельства подписи запросов, обновляемых API-настроек, проверки публичных ключей TLS и преобразования конфигурации. Точные алгоритмы, активный базовый адрес API, HTTP-методы, тела, формат подписи, назначение каждого заголовка и формат ответа ещё не восстановлены. Нельзя обещать работоспособность после одного HTTP-запроса с access key.

Порядок исследования: проверить наличие поддерживаемого экспорта/интерфейса; изучить bootstrap и преобразование конфигурации; при необходимости сравнить собственные авторизованные запросы с официальным клиентом в Linux-стенде. TLS-проверку сохранять. Стабильный идентификатор устройства хранить в volume, чтобы перезапуск контейнера не создавал новое устройство. Проверить, действительно ли этого достаточно для учёта устройств сервисом.

## Kill switch и жизненный цикл

В Linux ELF присутствует `killswitch_other.go`, реализация `killswitch.noop`, а `noop.Supported` возвращает false (`xor eax,eax; ret`). Поле `kill_switch` в API ядра поэтому не является доказательством защиты от утечек на Linux. При первом запуске проверить фактический ответ `status.kill_switch.supported`.

Для TUN-режима предусмотреть собственную политику nftables/iptables в network namespace контейнера: запрет прямого выхода приложений при старте, обрыве и падении ядра; разрешения для loopback, VPN endpoint и необходимых bootstrap/API/DNS-запросов. Политику IPv6 определить явно. Динамические адреса API и endpoint требуют обновления разрешений; полагаться только на наличие TUN-маршрута нельзя.

Скрипт `postinst` отдельно указывает, что desktop-демон не сохраняет start snapshot и GUI не восстанавливает обрыв автоматически. Следовательно, CLI должен владеть желаемым состоянием, переподключением и повторным получением конфигурации. Более старое замечание в `postrm` про snapshot не доказывает его наличие в текущем desktop-поведении.

Healthcheck проверяет готовность туннеля и прохождение трафика, а не только существование PID. Docker restart policy реагирует на выход процесса; unhealthy-статус сам по себе не перезапускает обычный Compose-контейнер. Фатальная ошибка управляющего процесса должна завершать контейнер с ненулевым кодом.

## Этапы реализации

1. **Проверить локальное ядро.** Извлечь бинарник в Linux/amd64-стенд, запускать напрямую без systemd и GUI. Проверить `hello`, `status`, `checkConfig`, `start`, `stop`, события и завершение. Начать с импортированной конфигурации собственного подключения. Результат: один запрос через штатное ядро, подтверждённый внешним трафиком.
2. **Зафиксировать контракт API.** Восстановить цепочку access key → профиль → список серверов → выдача конфигурации → преобразование в `start`. Зафиксировать HTTP-методы, подписи, сроки жизни конфигурации, ошибки и устройство. Результат: повторяемое подключение без участия GUI. Если API пока недоступен, режим импорта остаётся полезным, но не считается завершением полноценного клиента Sota.
3. **Написать CLI на Go.** Команды `login --key-file`, `servers`, `connect`, `disconnect`, `status --json`, `logs`, `doctor`, `run`. `connect` управляет уже запущенным управляющим процессом; `run` работает в foreground и владеет жизненным циклом контейнера. `--server` выбирать по реальным ID из API. Ключ из файла/stdin/Docker secret; конфигурации с credentials не включать в образ и логи.
4. **Упаковать Docker.** Multi-stage сборка CLI; извлечение только `kittend` из pinned `.deb`; небольшой Linux runtime с CA-сертификатами и необходимыми сетевыми инструментами. Writable volume для настроек/идентификатора, runtime-каталог для сокета, tmpfs по необходимости. Состав runtime уточнить после проверки DNS и сетевых зависимостей. Compose-примеры для TUN sidecar и приложения в общем namespace. ARM64 отдельным этапом с официальным ARM64-бинарником.
5. **Добавить восстановление и защиту трафика.** События + контроль состояния, ограниченный backoff, обновление конфигурации, корректные SIGTERM/SIGINT, блокировка прямого выхода до готовности и при сбоях. При отзыве ключа/истечении подписки выдавать понятную ошибку без бесконечного шторма запросов.
6. **Проверить приёмку.** Подключение по ключу с чистого volume; список/выбор сервера; внешний IP; TCP/UDP по требованиям; DNS и IPv6; рестарт контейнера; недоступный API; обрыв и принудительное завершение ядра; отсутствие прямого выхода при сбоях; sidecar; отсутствие секретов в логах/слоях образа. Отдельно проверить DNS в потребляющем контейнере.

Первая рабочая веха: **штатный `kittend` + импорт конфигурации + CLI + реальный запрос через VPN внутри Docker**. Затем вход по ключу и эксплуатационная надёжность. Не включать в MVP Telegram login, tray/desktop-интеграцию, per-app split tunneling, все платформы и переписывание VPN-протоколов.
